# Closed-loop testbed

Closed-loop results: Table V, Fig. 4, the low-capacity, cellular, random-loss, high-bandwidth and shared-bottleneck
batches, the native GCC calibration and the client cost. Section 1 needs only the package; sections 2 to 7 rebuild the
AlphaRTC testbed and rerun calls; section 8 shows how runs become the numbers in the paper.

Set the path placeholders once, from the package root, as in `docs/PACKAGE.md` (`/path/to/llm4bandpp` = package root,
`/path/to/testbed/results` = `external/testbed/results`). For a rerun also point `/path/to/testbed` at your testbed
working directory, `/path/to/alphartc/LLM4Band` at your app directory (section 4), `/path/to/storage` at a scratch disk
and `/path/to/tools` at your vmaf build.

Script versions. Each closed-loop batch of the paper ran with its own copy of the run script
(`scripts/alphartc/run_staleness_once_twocontainer_midsnap_vNN.sh`, which runs one call with sender and receiver in two
containers) and of the components it installs (estimator entry point, arm, probing envelope, collector, weight check).
All versions that a cited batch used are kept; a higher version marks a later batch, not a fix (`docs/GLOSSARY.md`,
"Components and their versions"). To rerun a result, use the versions that `docs/RESULTS_INDEX.md` lists for it; for
new experiments, start from the latest run script (v29). The parts of the run-script name, arm names, envelope and
collector versions and trace window ids (`arm_ch_x`, `gcc_pt125_c200`, `hd_c1`, `hd_r1`, `hd_t6`, ...) are defined in
`docs/GLOSSARY.md`.

## 1. Recompute without a testbed

Every closed-loop batch ships its per-run rows and judge output:

- 720p batches: `experiments/results/<batch>/runs_full.jsonl` (one row per run: validity, VMAF, SSIM, PSNR, freezes,
  utility, queueing, per-second video rate; columns in `data_dictionary.json`), `runs_tidy.csv`, `result_v1.json`,
  `contents.json`, `ceilings.json`, `layout.json`.
- 320×240 batches: `experiments/results/<batch>/runs.jsonl` and `result_v1.json`.
- Copies of the testbed-side files that the scripts read from `/path/to/testbed/results/<batch>/` (sequence lists,
  per-sequence video-rate ceilings, job lists, weight checks) and, for six 720p batches, per-frame VMAF (`quality_*.json`) and decoded-frame times
  (`decoded_timestamps_*.csv.gz`) of the deployed system (`arm_ch_x`) and the Python GCC.

Table V and Fig. 4 are regenerated by `scripts/paper/make_tables_v2.py` and `scripts/paper/make_fig_closedloop_v1.py`
(`docs/PACKAGE.md`, "Level 1 by hand"). To recompute a verdict from the per-run rows, use the batch's own judge function with the cells in the
order the batch used (condition-major, sequences from `contents.json`) and the valid runs in file order; the bootstrap
draws depend on that order. For the first 720p batch:

```python
import json, sys
sys.path.insert(0, "scripts/alphartc/deploy")
import hd720_ch_eval_v1 as E
rows = [json.loads(l) for l in open("experiments/results/hd720_closedloop_ch_v1/runs_full.jsonl")]
V = {}
for r in rows:
    if r.get("valid") and isinstance(r.get("vmaf"), (int, float)):
        V.setdefault((f"{r['cond']}__{r['video_id']}", r["arm"]), []).append(r["vmaf"])
C = json.load(open("experiments/results/hd720_closedloop_ch_v1/contents.json"))
cells = [f"{c}__{v}" for c in E.CONDS for v in C["main_contents"]]
print(E.judge(V, cells))   # holds, D = 4.5758, 90% interval [3.4411, 5.7402]; Table V: 4.6 [3.4, 5.7]
```

The other 720p batch scripts call the same `judge` with their own conditions, arm keys and references; see each
script's `judge()` (scripts per Table V row in `docs/RESULTS_INDEX.md`). The split into the first 30 s and the rest
(the ramp-up numbers of Section V-F) is `python3 scripts/paper/steady_state_qoe_v1.py run` for the five GCC batches;
for the cellular batch,
`python3 -c 'import sys; sys.path.insert(0, "scripts/paper"); import steady_state_qoe_v1 as S; print(S.batch("hd720-realtrace-ch-v1"))'`
reproduces `experiments/results/closedloop_steady_qoe_v1/realtrace_explore_v1.json` exactly.

The judges themselves (`<batch>.py judge`) read the raw per-run logs, which are not shipped (2.8 GB); they run on a
rerun's output (section 7).

## 2. Host

- Linux x86-64 with Docker. We used one laptop (Core i9-13900H, 20 threads, 30 GB RAM), Ubuntu 26.04, kernel 7.0,
  Docker 29.2.1, with the power profile set to balanced before each batch (`power_profile_v1.py`). CPU shares and
  latencies depend on the machine; the paper compares arms within a batch only.
- Kernel modules (load once as root; containers cannot load them):
  `modprobe -a ip_tables iptable_filter iptable_mangle nf_conntrack xt_conntrack sch_netem ip6_tables ip6table_filter ip6table_mangle xt_CLASSIFY`
- Containers run with `--cap-add NET_ADMIN`; shaping happens on the sender container's `eth0` (htb and netem built
  by comcast, then changed in place every second by `scripts/alphartc/comcast_policy_tcpudp_v3.sh`).
- Segmentation offload off on the sender: `gso_max_segs` of the sender's `eth0` must be 1, so that netem counts TCP
  packets, not 64 KB segments. The container's iproute2 cannot set it; use
  `docker exec -i -u root alphartc-sender-p1 python3 - set eth0 1 < scripts/alphartc/deploy/set_gso_netlink_v1.py`.
  The v2 scheduler (720p batches) checks and resets it before every run, and run scripts v17 and later refuse to start (exit 7) when
  `STALENESS_REQUIRE_GSO_SEGS=1` and the value differs. A container restart resets it.
- Disk: a 720p call writes about 5 GB of decoded video before the scheduler keeps every eighth frame; the job lists
  require 8 GB free on the results disk and 1.5 GB on the scoring scratch disk.
- Load: 720p batches ran on one or two container pairs with one scoring worker; arms that run an LLM on the
  receiver's CPU need about 4 cores and 3 GB per container pair.

## 3. Build AlphaRTC and the testbed image

AlphaRTC (https://github.com/OpenNetLab/AlphaRTC, BSD-3-Clause). We checked the source at commit
`d545f81f039ebe3f77ce97c7e72f97e5ab8abe29`; its README describes the build (`make all`: an Ubuntu 18.04 compile image
with depot_tools, `gclient sync`, `gn gen out/Default --args='is_debug=false'`, `ninja -C out/Default
peerconnection_serverless`). The build produces `peerconnection_serverless.origin` (the binary), the Python wrapper
`peerconnection_serverless`, AlphaRTC's ONNX inference libraries and `cmdinfer.py`.

The binaries our runs used (sha256 recorded in every run's `code_*.sha256`):

| File | sha256 |
|---|---|
| `/usr/bin/peerconnection_serverless.origin` (default cap 2500 kb/s) | `d02abb8306a131809320c0ff5b1bd185a8f444020fe4aa57d3b9a27a54f88761` |
| high-bitrate copy (cap 20000 kb/s), `/path/to/testbed/hb_v1/peerconnection_serverless.origin` | `1ff185744a306df642f716201c89edeecfee865613ee91859e4d7d5df1c1d5ea` |
| `/usr/bin/peerconnection_serverless` (wrapper; identical to `examples/peerconnection/serverless/peerconnection_serverless` at d545f81) | `ece405e406d7f1917b0d5aeff5a0daa7e4cc704b05a115f20029ad2201107477` |

The binary is dated 2021-05-12 and its source revision was not recorded, so a build at d545f81 will have another hash.
The part that matters for the video rate is the same in both: libwebrtc's `GetMaxDefaultVideoBitrateKbps` returns 600,
1700 and 2000 kb/s for frames of up to 320×240, 640×480 and 960×540 pixels and 2500 kb/s for larger frames, and the disassembly of our binary shows
exactly these thresholds and values.

High-bitrate variant (Section V-F, "cap raised to 20 Mb/s"). To build it from source, change the function
`GetMaxDefaultVideoBitrateKbps` in `media/engine/webrtc_video_engine.cc` (line 269 at d545f81):

```bash
sed -i '269s/max_bitrate = 2500;/max_bitrate = 20000;/' media/engine/webrtc_video_engine.cc   # check the line first
```

then rebuild and keep the binary as `/path/to/testbed/hb_v1/peerconnection_serverless.origin`. We ran a binary patch
of the original instead: `scripts/alphartc/deploy/patch_pcs_maxbitrate_v1.py ORIGINAL OUTPUT 20000` checks the
original hash `d02abb83...`, replaces the five bytes `B8 C4 09 00 00` (`mov $2500,%eax`, the only occurrence, at file
offset 0x5a4e21, virtual address 0x5a5e21) by `B8 20 4E 00 00` and gives `1ff18574...`. The lower tiers are untouched,
so 320×240 batches are unaffected. Run scripts v22 and later use the patched copy when `STALENESS_HIGH_BITRATE=1`.

The runtime image: `docs/Dockerfile.testbed` is a draft (not built by us) of an image equivalent to the one we used:
Ubuntu 18.04, the AlphaRTC files above, Python 3.9.16 as `/usr/bin/python3` with torch 2.5.1+cpu, numpy 1.26.3,
onnxruntime 1.19.2, transformers 4.47.1 and the rest of our pip freeze, iproute2, iptables, ffmpeg, and comcast
(github.com/tylertreat/comcast at 461b29c, built with Go 1.20.8; the comcast binary we used was built from a locally
modified checkout of that revision, and the modification was not recorded; comcast only sets up htb and netem, which
`comcast_policy_tcpudp_v3.sh` then changes in place, section 2). Tag it `alphartc4band:latest`, the name the scripts expect.
We do not distribute the image we used.

## 5. Network profiles

`scripts/alphartc/deploy/profiles/` holds the synthetic profiles (constant capacity with 50 ms delay, with or without
random loss) and the Chorus windows (CC BY 4.0, GreenLv/Chorus commit 8e1e26bc). A profile sets `rate` (kb/s) once
per second for real traces (`wait 1`) and has a queue length per job (95th-percentile rate times 250 ms, divided by 9600 bits).
Profiles cut from the UCC 4G (Raca et al., Zenodo 10.5281/zenodo.1219679) and Norwegian 3G/HSDPA (Riiser et al.)
traces are not redistributed. To rebuild them:

1. Download the raw traces, set `RAW` and `OUT` in `scripts/llm_kp/build_corpus_v1.py`, run it and copy the `corpus.jsonl` it
   writes to `OUT` to `data/llm_kp/corpus_v1.jsonl`, where the profile builders read it (ours: sha256 f2cf847d4f8b8db99a23375d3f176d5e7b34f18a55ba606ae8ed8876fefd24d0). The
   script also reads one more trace file that no profile uses; its docstring says how to build the corpus without it,
   in which case only the corpus hash differs.
2. For each missing profile, take its trace id and start second from the directory's `provenance.json` (stripped copy
   for `lowbw_real`: `scripts/alphartc/deploy/profiles_public/lowbw_real/provenance.json`) and write that window with the
   directory's builder (`make_hd720_real_profiles_v1.py`, `make_hd720_hb_profiles_v1.py`, `make_hd720_real8_profiles_v1.py`,
   `make_coldstart_real_profiles_v1.py`, `make_obsschema_*_profiles_v1.py`, `make_obsrepair_*_profiles_v1.py`,
   `make_lowbw_real_profiles_v1.py`). Do not rerun the selection rules from scratch: they exclude traces used by earlier
   profiles, some of which are not in this package, so the draw would differ.
3. Check each file against `body_sha256` in `scripts/alphartc/deploy/profiles_public/profile_sha256.json` (hash of the
   command lines; the comment header of a rebuilt file may differ).

Replay fidelity (`trace-replay-shaping-diag-v2`, `experiments/results/trace_replay_shaping_diag_v2/result.json`): over
120 one-second steps the schedule drifted by at most 0.031 s; a saturating probe received a median of 0.98 to 0.99 of the set rate
over its 5 s windows (all windows within 15%), and a probe below capacity lost no more than the set rate implies.

## 7. Run a batch

Each batch has one script under `scripts/alphartc/deploy/` with subcommands such as `jobs`, `judge` and `selftest` (names vary:
`hd720_attr_loss_v1.py` has `judge-attr` and `judge-loss`; the Usage line in most scripts' docstrings lists them), and
its registration text in `registry/`. The steps, in order:

```bash
D=scripts/alphartc/deploy; K=/path/to/testbed/results/hd720-closedloop-ch-v1
python3 $D/hd720_ch_eval_v1.py jobs                       # writes $K/main/jobs.json (arms, profiles, repetitions, order)
python3 $D/parallel_testbed_v2.py $K/main/jobs.json       # runs every job once on the pairs, scores, writes QUEUE_COMPLETE
python3 $D/hd720_ch_eval_v1.py judge                      # writes $K/result_v1.json and experiments/results/<batch>/runs_full.jsonl
```

The 320×240 batches write their job list to a path given on the command line and use the v1 scheduler, e.g.
`python3 $D/lowbw_ch_vs_conf_v1.py jobs $K/jobs_main.json; python3 $D/parallel_testbed_v1.py $K/jobs_main.json;
python3 $D/lowbw_ch_vs_conf_v1.py judge`. Where a batch loads several C-H checkpoints, run the weight check after the
scheduler and before judging (`seed_weight_check_vN.py $K`, version per batch in `docs/RESULTS_INDEX.md`): it
recomputes the model output of every run from its logged observations with each candidate checkpoint and names the one
that matches. Judges call `scripts/exp.py`, which here only appends to `experiments/registry_local.jsonl`.

Each job runs once; a failed or invalid run is kept and counted, never rerun, and a restarted scheduler skips jobs that
have a `run_meta.json`. Batches ran one after another, never two at once.

## 8. From runs to Table V and Fig. 4

A run is valid when it passes the run script's own checks (call length, decoded frames) and, in the 720p batches, those
of `hd720_run_metrics_v1.py` (quality scored, at least 90% of frame numbers read, VMAF computed, CPU package temperature below
95 °C, the same code hashes as the other runs of its arm), plus the batch script's envelope check for enveloped arms;
invalid runs stay in `runs_full.jsonl` with their reasons. Scoring, done on the host by the scheduler
(`qoe_quality_once_v3.py` for 720p, `qoe_quality_once_v2.py` for 320×240): tesseract reads the burned frame number of every eighth (720p) or fourth (320×240) decoded
frame, the matching source frame is paired with it, ffmpeg computes SSIM and PSNR and the vmaf tool VMAF (model
`vmaf_v0.6.1`, after bicubic upscaling to 1920×1080), all on the region above the label band. Utility, queueing and
loss come from the receiver's network log (`eval_staleness_run.py`, 500 ms queueing bound), freezes from the
decoded-frame times with the W3C WebRTC statistics freeze rule (Section S7). Tool versions on the scoring host, as read after the last batch: vmaf 3.2.0
built from Netflix/vmaf commit f85a853 (model file sha256 5950d61f...), ffmpeg 8.0.1-3ubuntu2, tesseract 5.5.0 with
leptonica 1.86.0, Python 3.14.4 with Pillow 12.1.1; the weight checks used Python 3.11.13 with torch 2.14.0.

Each Table V entry is a registered reading of one batch: the mean over cells (condition × sequence) of the difference in
mean VMAF between the valid runs of our arm and of the reference, with a 90% interval from 10 000 bootstrap draws that resample
valid runs within each cell and arm. The status letter is the registered verdict (P: after the post hoc revision recorded
in the registry). `make_tables_v2.closedloop_rows` takes these readings from `experiments/registry.jsonl` and the result
files, `make_fig_closedloop_forest_v2.rows_v2` groups them.

`docs/RESULTS_INDEX.md` lists the batch, batch script, run script, arm settings and weight check of every Table V row,
Fig. 4 panel and closed-loop result in the text.

Native GCC calibration: gcc-native-calib-v1 (`scripts/gcc_native/run_gcc_native_v1.sh`, `gcc_native_calib_v1.py`).
Client cost (Table III):
`python3 scripts/measure_client_hardware_v5.py --code scripts/alphartc/deploy/nl_estimator_v1/src --stats experiments/results/client_hw_hcq_v1_public/input_stats_mre4.json --config QWEN/config.json --out OUT.json --arms ch,hcq,full_conf --devices cpu,cuda:0`
(QWEN is a local copy of Qwen/Qwen1.5-0.5B; the arm keys `ch`, `hcq` and `full_conf` are defined in
`docs/GLOSSARY.md`).
